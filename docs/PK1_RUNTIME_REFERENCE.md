# PK1-era runtime reference and adoption boundary

## Purpose

This note records what may be learned from related public projects while
keeping Gas1's mechanism and electron-collision data independently auditable.
It is a design reference, not a vendored dependency and not a data import.

## Sources consulted on 2026-09-17

| Source | What it establishes | Adoption boundary |
| --- | --- | --- |
| [DFT-microkinetic](https://github.com/wwwccttoo/DFT-microkinetic) | The Shao/Mesbah work uses ZDPlasKin, is adapted from Hong/Murphy code, and distributes a corrected QtPlaskin package. | Use it to compare the project layout and user-code workflow. Do not assume its data files are Gas1-compatible. |
| [qtplaskin wrapper](https://github.com/aluque/qtplaskin/blob/master/zdplaskin.py) | The generated kinetic module exposes initialization, conditions, density set/get, solver configuration, and timestep calls. | Use the call sequence as an interface reference; do not import its legacy Python package. |
| [ChemPlasKin](https://github.com/ShaoX96/ChemPlasKin) | A modern workflow keeps the reaction mechanism and electron-collision data as separate inputs. | Reinforces the separation already used by this repository; it is not a drop-in replacement for ZDPlasKin. |
| [ZDPlasKin examples](https://www.zdplaskin.laplace.univ-tlse.fr/examples/index.html) | A minimal user program initializes the module, sets conditions/densities, and advances by timestep calls. | The local vendor preprocessor remains the compiler-facing source of truth. |

## Adopted organization

The new local execution path is intentionally narrow:

```text
versioned YAML case
    -> configuration validation
    -> BOLSIG label/data audit
    -> case-local staging of vendor runtime and approved database
    -> generated Fortran closed-0D pulse driver
    -> ZDPlasKin preprocessor
    -> gfortran compilation and BOLSIG link
    -> isolated horizon work directories and manifests
```

This preserves the useful PK1-era separation between a reusable driver
generator and generated Fortran user code, while moving machine-local paths
out of the scientific workflow.

## Interface adopted in `src/pk2_pulse/driver.py`

The generated driver uses the conventional ZDPlasKin sequence:

1. `ZDPlasKin_init()`;
2. `ZDPlasKin_set_config()` for solver tolerances;
3. `ZDPlasKin_set_conditions()` for gas temperature and each pulse-phase
   reduced field;
4. `ZDPlasKin_set_density()` for N2, H2, and fixed electrons;
5. repeated `ZDPlasKin_timestep(time, dtime)` calls, with the caller advancing
   its pulse clock; and
6. `ZDPlasKin_get_density()` calls to create a concise phase-endpoint CSV.

The generated program is restricted to a closed gas-phase reactor: it has no
CSTR source term, feed, outlet, surface-site initialization, or active surface
reaction control.

## Explicit non-adoptions

- No `F:\\Codex\\PK1\\...` location is used by the new modules.
- No `zdp_gui` or `zdp_runtime` helper module is imported.
- No source code, collision data, or generated outputs are copied from an
  external GitHub project.
- The existing `GasPulse/0D/scripts/` files remain historical references;
  their accepted trajectories are not modified or regenerated by this work.

## Compatibility check needed after data unblocks the run

The local vendor `preprocessor.exe` generates the final Fortran module and is
therefore authoritative for the precise module ABI.  Once an approved
`bolsigdb.dat` is available, run a foreground one-cycle smoke test before the
parallel time scan.  That test must verify preprocessing, compile/link order,
CSV phase order, initial pressure/composition/electron density, and the
requested final time.
